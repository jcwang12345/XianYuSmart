# 鱼麦多功能对标与 XianyuSmart 补强建议

> 调研日期：2026-09-13
> 调研范围：鱼麦多公开官网、登录页、服务条款、隐私政策，以及当前本地 XianyuSmart 代码。未登录鱼麦多付费工作台，因此以下鱼麦多能力属于公开产品声明，并非对其内部实现的独立验证。

## 一、结论

鱼麦多对当前系统最有价值的补充，不是简单增加几个页面，而是把“能自动回复、能自动发货”的工具，升级成适合 20～30 个账号协同运营的工作台。

当前系统已经具备多账号、消息、关键词与 AI 回复、订单同步、虚拟商品自动发货、通知中心、评价、买家档案、账号续期和基础数据面板等主干能力。与鱼麦多相比，最明显的差距集中在六处：

1. 缺少跨账号的异常优先工作台；
2. 缺少真正的团队、租户成员和按店授权模型；
3. 商品发布与批量经营能力不完整；
4. 实物物流、退款、纠纷等售后闭环不足；
5. 平台违规、短信/人脸验证和申诉没有形成统一任务中心；
6. 缺少账号、店铺、商品、客服和退款维度的经营分析。

建议吸收鱼麦多的“运营闭环”思路，但不照搬 SaaS 计费、插件市场和第三方虚拟容器。我们是自部署系统，应优先保持账号凭证和业务数据本地化。

## 三、最值得采纳的产品设计

### 1. 建立“账号运营驾驶舱”

首页不要只展示总订单数，而要优先回答：哪个账号现在需要人处理。

每个账号至少展示：

- 在线/掉线/授权即将过期；
- 未读咨询、超时未回复；
- 待发货、发货失败、退款待处理；
- 验证码、人脸、处罚、申诉截止时间；
- 今日订单、收入、退款率；
- 最近一次消息、订单、Cookie 和 WebSocket 成功时间。

支持按严重度排序、一键筛选“只看异常”、批量认领、跳转到对应会话或订单。20～30 个账号时，这是收益最高的改造。

### 2. 把所有高风险异常变成有状态的任务

账号验证、发货失败、退款、纠纷不能只发一条企业微信通知。统一任务状态建议为：

`待处理 → 已认领 → 处理中 → 已恢复/已完成 → 已忽略`。

任务需要保留账号 ID、账号备注、订单/会话、严重度、截止时间、负责人、通知送达记录和完整时间线。相同事件使用幂等键合并，状态未变化不重复推送；超时未处理再升级通知。

### 3. 商品发布升级为“草稿—预检—发布—校验”

商品发布应拆成四阶段：

1. 草稿：商品类型、分类、结构化属性、SKU、库存、价格、运费模板、图片、视频和服务承诺；
2. 预检：必填项、价格/库存规则、图片视频规格、敏感词和能力权限；
3. 发布：异步任务，逐账号、逐商品记录结果；
4. 校验：回读平台商品，确认标题、价格、库存、运费、媒体和活动是否实际生效。

粉丝价、小刀、闲鱼币、曝光推广、佣金等功能必须先做“账号能力探测”，只在平台接口或商家权限真实可用时开放，不能把本地状态误当作平台已生效。

### 4. 完整订单和售后工作台

在现有自动发货队列之上补齐：

- 实物商品选择地址、物流公司、运单号及轨迹；
- 卖家旗标、内部备注、客服协作备注；
- 改价、同意/拒绝退款、部分退款及证据附件；
- 催收货、邀请评价、自动评价的策略与冷却期；
- 平台纠纷/小法庭、申诉截止时间和材料清单；
- 所有外部动作的幂等键、回读确认和审计记录。

退款、删除商品、批量改价、真实发货等不可逆动作不应由 AI 直接执行；AI 可以整理证据、生成草稿，最终通过确认卡片由人批准。

### 5. 真正实现团队按店协作

当前 ADMIN/USER 不足以支撑多人共同管理 20～30 个账号。建议引入：

- `tenant`：店群经营主体；
- `tenant_member`：用户加入哪个经营主体；
- `member_role`：负责人、管理员、运营、客服、财务、自定义角色；
- `member_account_scope`：成员可以访问哪些闲鱼账号；
- `permission`：查看、回复、发货、退款、商品编辑、凭证管理、系统配置等动作；
- `operator_id/operator_name`：所有关键操作写入实际操作者；
- 高风险动作二次确认，必要时双人审批；
- TOTP 两步验证、恢复码、登录设备列表和强制下线。

这项改造必须先处理当前“平台用户 ID 默认兼作 tenant_id”的模型，否则新建客服用户会变成另一个租户，无法安全地共享指定店铺。

### 6. 先建设内部事件平台，再考虑插件市场

没有必要现在复制鱼麦多完整插件市场。先定义稳定的领域事件：

- `account.offline`、`account.auth_expiring`、`risk.created`；
- `message.received`、`conversation.sla_breached`；
- `order.paid`、`delivery.failed`、`refund.requested`；
- `goods.publish_failed`、`goods.inventory_low`。

通过 outbox 保证不丢事件，Webhook 使用 HMAC 签名、重试、死信和订阅权限。以后出现多个扩展需求，再在该基础上增加内部插件注册表。

## 四、实施顺序与验收标准

### P0：可靠运营闭环

1. 账号运营驾驶舱；
2. 风险/验证/处罚统一任务中心；
3. 商品发布字段、预检、异步发布及回读校验；
4. 批量商品操作任务化并提供逐项结果；
5. 发货/退款/订单异常统一工作台；
6. 通知幂等、认领、关闭和超时升级。

验收：30 个账号并发运行时，可在一个页面找到所有异常；网络波动不会造成重复发货或重复待发货通知；批量发布失败能准确定位到具体账号、商品、字段和平台返回。

### P1：团队和经营能力

1. tenant_member、五类预置角色、按账号授权；
2. 操作者级审计、CSV 导出；
3. TOTP、恢复码和会话设备管理；
4. 跨店客服收件箱、认领与 SLA；
5. 实物物流、退款和纠纷闭环；
6. 店铺/商品/客服/退款/账号健康看板。

验收：客服只能看到获授权账号；财务只能查看经营数据；管理员可以追溯是谁在什么时间回复、发货、退款或修改商品；离职人员能立即撤销全部会话和店铺权限。

### P2：平台经营扩展

1. 粉丝价、小刀、闲鱼币及推广能力适配；
2. HMAC Webhook 和内部扩展机制；
3. AI 客服质检、回复建议和售后材料草稿；
4. 平台官方授权适配器（在获得相应资格后）。

验收：所有平台经营功能都有能力检测、权限提示、执行确认、回读校验和失败降级；不存在“页面显示成功、平台实际未生效”的假状态。

## 五、不建议直接照搬的部分

1. **SaaS 套餐和计费**：当前是自用部署，短期没有收益；
2. **完整插件市场**：治理、权限和供应链成本高，先做内部事件总线；
3. **第三方虚拟容器保存登录态**：鱼麦多隐私政策披露其登录态刷新和转发会涉及第三方服务；本系统应默认本机加密存储，外部适配器可选且可审计；
4. **AI 直接执行不可逆操作**：AI 应生成建议和草稿，退款、发货、删除、批量改价必须确认；
5. **未验证的推广功能**：不得用本地“推广状态”代替闲鱼平台真实推广结果。

## 六、建议的数据和安全底座

- Cookie、sessionKey 等凭证字段使用独立密钥加密，接口默认永不返回原文；
- “查看/复制凭证”仅限高权限临时解密，并写入审计；
- 每账号保持独立 CookieJar、设备配置、WebSocket、限速器和失败熔断；
- 关键外部动作采用业务幂等键，并保存请求、平台受理结果和回读结果；
- 通知、Webhook 和批量任务统一使用 outbox/任务表，支持重试、死信和人工重放；
- 敏感买家数据发送给大模型前脱敏，日志禁止记录完整 Cookie、手机号和地址；
- 所有时间敏感任务保存平台截止时间，提前多级提醒。
